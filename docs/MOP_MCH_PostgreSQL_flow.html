১ · সিস্টেম আর্কিটেকচার ও কম্পোনেন্ট

সিস্টেমটি PostgreSQL-কেন্দ্রিক (single source of truth) আর্কিটেকচার অনুসরণ করে: প্রতিটি লেখা (write) সরাসরি সার্ভারে যায় ও PostgreSQL-এ স্থায়ী হয়; প্রতিটি পড়া (read) অনলাইনে সার্ভার থেকে রিফ্রেশ হয়। ডিভাইসের লোকাল SQLite শুধু offline cache — ইন্টারনেট না থাকলে সর্বশেষ synced ডেটা দেখায়।

কম্পোনেন্টপ্রযুক্তিদায়িত্ব
Flutter মোবাইল অ্যাপ
(Field App + Admin Portal)		Flutter 3.22+, provider, dio, sqfliteস্বাস্থ্যকর্মীর মাঠের কাজ (নিবন্ধন, ANC visit, child assessment) এবং সুপারভাইজারের পোর্টাল (dashboard, worker onboarding)। sqflite = শুধু read-cache।
Spring Boot API
(Backend)		Java 21, Spring Boot 3.3.5, JPA + Flywayসব business logic: login যাচাই, RiskService (ANC ঝুঁকি) ও NutritionService (MUAC/SAM/MAM) ক্লাসিফিকেশন, credential জেনারেশন, dashboard aggregation।
PostgreSQL
(Database)		PostgreSQL (Windows-এ নেটিভ), schema Flyway-managedসব দীর্ঘমেয়াদী ডেটা: users, workers, beneficiaries। Hibernate ddl-auto: validate — schema-র মালিক Flyway migration।

২ · এন্ড-টু-এন্ড ডেটা ফ্লো

ফ্লো A — Field officer অ্যাকাউন্ট তৈরি (Admin onboarding)

Username/password সার্ভারে তৈরি হয় — admin যা দেখেন হুবহু তা-ই ডাটাবেজে থাকে, তাই লগইন কখনো mismatch হয় না। সার্ভারে না পৌঁছালে অ্যাপ স্পষ্ট এরর দেখায় — অসম্পূর্ণ "ভূতুড়ে" অ্যাকাউন্ট তৈরি হয় না।

ফ্লো B — নতুন মা/শিশু নিবন্ধন (Registration, write-through)

ফ্লো C — ক্লিনিক্যাল ভিজিট ও সার্ভার-সাইড ঝুঁকি নির্ণয়

ভিজিটEndpointসার্ভারে কী হয়
ANC visit
(গর্ভবতী মা)		POST /api/beneficiaries/{id}/anc-visitRiskService: SBP ≥ 140 বা DBP ≥ 90, Hb (রক্তস্বল্পতা), danger signs ইত্যাদি থেকে High/Medium/Low নির্ণয় → beneficiary আপডেট → PostgreSQL-এ সেভ → আপডেটেড রেকর্ড অ্যাপে ফেরত।
Child assessment
(শিশু)		POST /api/beneficiaries/{id}/child-assessmentNutritionService: MUAC < 11.5 cm বা edema → SAM (High), 11.5–12.5 → MAM (Medium), নাহলে Normal → PostgreSQL-এ সেভ।
Live previewPOST /api/risk/anc, /api/nutrition/muacফর্মে টাইপ করার সাথে সাথে লাইভ ক্লাসিফিকেশন — persist করে না।
কেন সার্ভার-সাইড ক্লাসিফিকেশন? অ্যাপ ও পোর্টাল একই RiskService ব্যবহার করে, তাই একটি কেসের ঝুঁকি-স্ট্যাটাস নিয়ে দুই জায়গায় কখনো ভিন্ন ফল আসে না; ক্লিনিক্যাল নিয়ম বদলাতে হলে শুধু ব্যাকএন্ড আপডেট করলেই সব ক্লায়েন্ট নতুন নিয়ম পায়।

ফ্লো D — পড়া (Read-through) ও অফলাইন আচরণ

অবস্থাআচরণ
অনলাইনপ্রতিটি তালিকা-লোডে অ্যাপ আগে GET /api/beneficiaries / GET /api/workers কল করে, সার্ভারের authoritative snapshot দিয়ে SQLite cache পুরো রিফ্রেশ করে, তারপর UI-তে দেখায়।
অফলাইনসার্ভার call ব্যর্থ হলে সর্বশেষ cached snapshot থেকে পড়া হয় — মাঠকর্মী তালিকা দেখতে পান। লেখা (নতুন নিবন্ধন/ভিজিট) অফলাইনে ব্লক — অ্যাপ বাংলা+ইংরেজি এরর দেখায়, যাতে ডাটাবেজে না-পৌঁছানো এন্ট্রি "সেভ হয়েছে" বলে ভুল ধারণা না হয়। (Roadmap: durable offline write-queue, সেকশন ৮)

ফ্লো E — তদারকি (Supervision)

সুপারভাইজার পোর্টাল GET /api/dashboard ও GET /api/indicators কল করে PostgreSQL-এর লাইভ ডেটা থেকে কভারেজ, ঝুঁকি-বণ্টন ও পুষ্টি পরিসংখ্যান দেখেন — field officer-দের সাম্প্রতিক এন্ট্রিগুলো সাথে সাথেই প্রতিফলিত হয়।

ধাপ ১.১ — PostgreSQL-এ ডাটাবেজ ও ইউজার তৈরি

pgAdmin অথবা psql টার্মিনালে (postgres superuser হিসেবে):

-- ইউজার না থাকলে তৈরি করুন
CREATE USER zahra WITH PASSWORD 'zahra';
-- ডাটাবেজ তৈরি করে zahra-কে Owner বানান (Flyway-র টেবিল CREATE করার অধিকার লাগে)
CREATE DATABASE preventive_healthcare OWNER zahra;

যাচাই: psql -U zahra -d preventive_healthcare -h localhost দিয়ে ঢোকা গেলে ✔

৮ · Optimization Roadmap ও নিরাপত্তা নোট

৮.১ — এখনকার ডিজাইনে যা নিশ্চিত

  • SoT সব read/write PostgreSQL-কেন্দ্রিক — এক সত্য উৎস, রিপোর্টিং সবসময় সঠিক।
  • Consistency Credentials ও ঝুঁকি-স্ট্যাটাস সার্ভার-জেনারেটেড — অ্যাপ/পোর্টাল/DB কখনো অমিল হয় না।
  • Safety সার্ভারে না-পৌঁছানো লেখা ব্যর্থ হিসেবে স্পষ্ট দেখানো হয় — নীরব ডেটা-হারানো নেই।
  • Offline read সংযোগ গেলেও মাঠকর্মী সর্বশেষ synced তালিকা দেখতে পান।

৮.২ — পরবর্তী optimization (অগ্রাধিকারক্রমে)

#উন্নতিবিবরণ ও লাভ
1Durable offline write-queueঅফলাইনে নিবন্ধন/ভিজিট full payload-সহ লোকাল কিউতে রাখা, অনলাইন হলে আসল endpoint-এ replay (বর্তমান /api/sync শুধু ack করে)। প্রত্যন্ত অঞ্চলে অফলাইন লেখাও সম্ভব হবে।
2Password hashing + টোকেনBCrypt hash, প্রথম লগইনে বাধ্যতামূলক password বদল, JWT session। প্রোডাকশনের পূর্বশর্ত।
3Delta syncupdated_at/ETag ভিত্তিক — পুরো তালিকার বদলে শুধু পরিবর্তিত রেকর্ড টানা; মোবাইল ডেটা ও লোড-টাইম কমে।
4Pagination + server-side filterUnion/ঝুঁকি অনুযায়ী সার্ভারে ফিল্টার — হাজারো beneficiary-তেও পোর্টাল দ্রুত।
5Optimistic UI + retry/backoffরেসপন্সের আগেই সাময়িক প্রদর্শন, ব্যর্থে rollback; নেটওয়ার্ক flaky হলে স্বয়ংক্রিয় পুনঃচেষ্টা।
6Background sync workerঅ্যাপ বন্ধ থাকলেও নির্দিষ্ট বিরতিতে কিউ flush (WorkManager)।

৮.৩ — নিরাপত্তা নোট

  • ডেমো credentials (s.rahman/Admin-2026 ইত্যাদি) ও plain-text password শুধু ডেমো বিল্ডের জন্য — প্রোডাকশনে hash + টোকেন বাধ্যতামূলক।
